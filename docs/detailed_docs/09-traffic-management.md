# Traffic Management and Other Structures

## Objects attached to the network

The network describes where vehicles can drive. Everything that *manages* that traffic is declared separately, usually in additional files, and attached to lanes, edges or junctions by identifier. This separation means a single network can be paired with many control strategies, and it explains why changing signal timing or adding a parking area never requires rebuilding the network.

## Traffic lights

A traffic light in SUMO is a **program** that cycles through **phases**, each phase assigning a signal character to every controlled connection of a junction. A `tlLogic` element carries an identifier that must match a signal in the network, a `programID`, a `type`, an `offset` and a list of phases, each with a duration and a state string:

```xml
<tlLogic id="J1" programID="peak" type="static" offset="0">
  <phase duration="31" state="GGggrrrr"/>
  <phase duration="4"  state="yyggrrrr"/>
  <phase duration="31" state="rrrrGGgg"/>
</tlLogic>
```

The character at position *i* describes the connection with link index *i*. Link indices run clockwise from north, with right turns before straight movements before left turns, and joined signals continue the numbering across junctions. The meaning of each character matches the decisions in [08-driver-decision-making.md](08-driver-decision-making.md): uppercase `G` is green with priority, lowercase `g` is green that yields to conflicting streams, `r` is red, `y` is yellow, `u` is red-yellow before green, `s` is a stop-then-go for right turns on red, and `o` and `O` represent a switched-off signal with and without priority, which makes drivers treat the junction as unsignalised.

Four **control types** exist. A **static** program uses fixed durations and a fixed cycle. An **actuated** program gives each phase a minimum and maximum duration and extends a green while detectors, created automatically upstream of the stop line, see a vehicle within a maximum gap, with parameters for the detector distance, the passing time and a jam threshold above which stationary vehicles are ignored; the `next` attribute lets a phase branch to alternative successors, which permits skipped left-turn phases, and `earliestEnd` and `latestEnd` support coordination into green waves. A **delay-based** program extends a phase according to the accumulated time loss of vehicles within a detector range. A **NEMA** program follows the American controller standard. Beyond these, expressions that depend on detector values allow custom switching rules without scripting.

Several programs may be loaded for one signal, and the last one loaded is active unless switched by a weekly automation definition or by TraCI. A program named `off` switches the signal off. Signals can be generated by netconvert with default settings (`--tls.guess`, green and yellow times, phase offsets), and the output programs are meant as starting points rather than calibrated plans. At runtime, an external controller can set the current phase, extend or shorten it, set a complete state string (which suspends automatic control) or install a new program, and signals report their phase, remaining time and controlled lanes, which is how adaptive and learning controllers are built. Rail signals are a separate mechanism, described in [10-traffic-modes.md](10-traffic-modes.md).

## Public transport facilities

Stops are the traffic-management object for public transport. Bus, tram, train and container stops are lane segments with a capacity for waiting persons and, optionally, access links from other edges. Because they are placed in the additional files and referenced by vehicles in stops, a timetable is a property of the demand while the facility is a property of the infrastructure. Details of schedules and persons boarding are covered in [03-demand-modelling.md](03-demand-modelling.md).

## Variable speed signs

A variable speed sign changes the speed limit of a set of lanes over time. It is defined by identifier and lanes and a list of steps, each saying that from a given time the limit is a given speed, with a negative value restoring the network default:

```xml
<variableSpeedSign id="vss0" lanes="a_0 a_1">
  <step time="0" speed="27.8"/>
  <step time="600" speed="13.9"/>
</variableSpeedSign>
```

Since the speed limit enters every driver's target speed, as explained in the previous essay, the sign influences all vehicles on those lanes at once. Steps may be stored in an external file for reuse.

## Rerouters

A rerouter is an object that acts on vehicles when they reach given edges, during specified time intervals and with a given probability of being heeded. It can close an edge or lane to some or all vehicle classes (`closingReroute`, `closingLaneReroute`), assign a new destination chosen from weighted alternatives (`destProbReroute`), assign a predefined route (`routeProbReroute`), or divert a vehicle to another parking area when its destination is full (`parkingAreaReroute`). Rerouters model both physical incidents and information signs. The outcome for a particular vehicle depends on whether the closure is hard (the permissions actually change) or soft (the edge remains usable but the sign suggests avoiding it), on the available alternatives, on how far upstream the vehicle passes the sign, and on how the vehicle was defined, and outcomes include rerouting at departure, ignoring the closure, waiting, or an error.

## Vaporizers and calibrators

A **vaporizer** removes every vehicle that enters a given edge during a time window, a blunt but useful tool for modelling a sink or for debugging. A **calibrator** is a more refined means of forcing simulated traffic to match observations. On a lane or edge it measures passing flow and, depending on the settings in its flow definition, removes vehicles when the flow exceeds a target `vehsPerHour`, inserts vehicles with a given route and type when it falls short, sets the speed (acting then as a variable speed sign), and changes the type of passing vehicles. It can also clear unexpected jams relative to the expected flow. Type calibration does not work with the mesoscopic model.

## Parking areas

A parking area is a lane segment with a capacity composed of a roadside capacity and optional individually placed spaces, each of which can have its own position, angle, width and length, which allows fishbone and perpendicular layouts. A vehicle parks by having a stop on the parking area, which must lie on an edge of its route, and the vehicle leaves the traffic flow while parked, so that it does not block the lane, unlike an ordinary stop on the road. Manoeuvring into and out of angled spaces takes extra time, and a badge system can restrict a parking area to authorised vehicles. If a parking area is full, vehicles with the right device or a rerouter reroute to an alternative. Parking areas also serve as taxi stands and as transfer points between car and walking in intermodal trips.

## Turnarounds

Where a vehicle's origin or destination does not match its direction of travel, it may have to perform a U-turn at a junction. Turnarounds are created by netconvert at most junctions, and they are a common source of jams and deadlocks, since a turning vehicle crosses all lanes. Remedies are to route between junctions or between traffic analysis zones so that vehicles choose their initial direction, to remove loops from routes, and to restrict where netconvert creates turnarounds with the `--no-turnarounds` options for all junctions, signalised junctions, geometry-like nodes (the default), everything except dead ends or turn lanes, and the network fringe.
