# Network Building

## The SUMO road network as a model

A SUMO network is a directed graph of **junctions** (also called nodes) joined by **edges**, where an edge is a one-way road segment. A two-way street is therefore two edges, one per direction. Each edge is subdivided into one or more **lanes**, numbered from zero at the right-most lane, and the lane, not the edge, is where vehicles actually live: every lane carries its own speed limit, permitted vehicle classes, width and shape, although all lanes of an edge share a single length value even when curvature makes the outer lane geometrically longer. This single-length convention is a deliberate simplification, and it explains why the driving length used by the simulation can differ slightly from the length you would measure on the drawn geometry.

What distinguishes SUMO's network from a simple road graph is that it models the *inside* of intersections explicitly. Between every incoming lane and every outgoing lane that a vehicle may legitimately use, the network contains a **connection**, and unless disabled each connection traverses an **internal lane** that lies on an **internal edge** named with a leading colon, such as `:junction7_3`. Internal lanes give turning movements a real geometry and length, let the simulator compute a speed limit from the turning radius (using a square-root rule of the form speed equals the square root of radius times a factor of about 5.5), and carry the right-of-way logic. Where a vehicle might need to wait inside an intersection, for example a left-turner yielding to oncoming traffic, netconvert inserts an **internal junction** that splits the internal lane so the vehicle can stop at the conflict point. The legacy mode `--no-internal-links` removes all of this and makes vehicles jump over junctions, which is faster to build but less realistic.

Right-of-way is encoded per junction as a request matrix. For each connection index the junction records a bitstring of connections that have higher priority and must be yielded to, a larger set of foes that conflict at all, and a flag saying whether a vehicle may wait inside the intersection. Traffic lights are stored as `tlLogic` elements holding phases whose state string assigns one signal character to each controlled connection. The network also holds a `location` element describing the coordinate system. SUMO uses Cartesian metric coordinates with the origin shifted so that the network's lower-left corner is near zero, and keeps the offset and the projection parameters so that geographic coordinates can be recovered. Roundabouts are recorded as lists of nodes and edges because they affect both priority and lane-change decisions.

The compiled `.net.xml` file is meant for the simulator, not for people. It contains interdependent data structures, so the documentation insists that it should never be edited by hand. The supported workflow is to describe or convert the network, let netconvert compile it, and to modify it by exporting back to plain XML or using netedit.

## Plain XML networks

The editable representation consists of up to five cooperating files that netconvert merges. The **nodes file** declares junctions by identifier and coordinates and optionally their type. The **edges file** declares directed roads between nodes with a lane count, a speed, a priority and optionally permitted vehicle classes. The **connections file** overrides the automatic guesses about which lane leads to which. The **types file** collects defaults that edges can reference by name, so that "primary road" is defined once. The **traffic-light file** embeds signal programs. A minimal network needs only nodes and edges:

```xml
<nodes>
  <node id="0" x="0" y="0" type="traffic_light"/>
  <node id="1" x="-500" y="0" type="priority"/>
</nodes>
<edges>
  <edge id="1si" from="1" to="0" priority="3" numLanes="3" speed="13.89"/>
</edges>
```

compiled with `netconvert --node-files n.nod.xml --edge-files e.edg.xml --output-file net.net.xml`. When connections are not given, netconvert infers lane-to-lane links heuristically from lane counts and geometry, and the rest of the compilation (junction shapes, priorities, internal lanes, signals) is also computed automatically.

The **junction type** is the main way to tell netconvert how an intersection is regulated. A `priority` junction gives way according to edge priority and speed, a `traffic_light` junction is signal-controlled, `right_before_left` applies the continental yield-to-the-right rule, `allway_stop` makes everybody stop, `zipper` makes merging vehicles interleave, and `unregulated` performs no collision checking at all. A `rightOfWay` attribute selects the algorithm that ranks approaching edges, with variants that use only edge priority or mimic all-way-stop behaviour when a signal is off. Edge attributes such as `spreadType` control how lanes flare away from the edge centreline, `allow` and `disallow` restrict vehicle classes, and a nested `lane` element lets one lane differ from its siblings, for instance a bus lane. Connection attributes such as `pass`, `keepClear`, `visibility` and a custom crossing `speed` tune specific movements, and a `prohibition` element states explicitly that one movement must yield to another.

## Importing non-SUMO networks

netconvert reads a wide range of formats, and most conversions are a single option naming the source format plus an output file. It can import VISUM and Vissim models from PTV, OpenDRIVE, MATsim networks, ArcView shapefiles, DLR-Navteq road data, RoboCup rescue maps and OpenStreetMap. In practice OpenStreetMap is the dominant source. The command `netconvert --osm-files city.osm.xml -o city.net.xml` projects the WGS84 data to UTM automatically, but a raw conversion produces a network that suits only casual experimentation, and the documentation recommends a standard set of options: `--geometry.remove` to simplify chains of degree-two nodes, `--ramps.guess` to add the acceleration lanes OSM often omits, `--junctions.join` to merge clusters of nodes that really form one intersection, `--tls.guess-signals` to recover traffic-light positions that OSM stores on upstream nodes rather than on the junction, `--tls.discard-simple` and `--tls.join` to prune and synchronise signals, and `--tls.default-type actuated` for traffic-responsive control instead of fixed timing.

The choice of **typemap** has a large effect because OSM carries tags, not simulator parameters. A typemap translates highway classes into lane counts, speeds and permitted vehicle classes. SUMO ships maps for the default case, for German urban speed limits, for sidewalks and pedestrians, for bicycles, for ships and for bidirectional railways, and a chosen map is loaded in addition to, not instead of, the base map. Further options handle left-hand traffic (`--lefthand`), bicycle access tags, imported sidewalks, and turn-lane markings. Large areas are reduced with edge filters such as `--keep-edges.by-vclass passenger` and `--remove-edges.by-type`. Typical OSM pitfalls are unjoined junction clusters, which cause deadlocks and artificially low throughput, misaligned signals at adjacent junctions, and tram tracks that share space with roads and need `--edges.join-tram-dist`.

For people who do not want to assemble this by hand, `osmWebWizard.py` offers a "three-click" scenario generator. The user selects a map region in a browser, chooses which traffic modes to generate, and the tool downloads the OSM data, applies suitable typemaps and options, builds the network, generates random demand for each selected mode and opens sumo-gui. Its output is a timestamped directory including a build script, which makes it a convenient starting point that can then be customised. For larger areas, `osmGet.py` downloads tiles by bounding box and `osmBuild.py` runs netconvert and polyconvert with chosen options.

## Generated, edited and enhanced networks

`netgenerate` creates abstract networks without any real-world data. A grid network is defined by the number of junctions and the spacing between them, a spider network by the number of arms and concentric circles, and a random network by edge probabilities, angle limits and distance ranges. They share options for turn lanes, default junction types and random perturbation of node coordinates. Abstract networks are useful for controlled experiments, since geometry cannot confound the effect under study, but they deliberately sometimes shorten geometric length while preserving driving distances.

`netedit` is the graphical counterpart of the plain-XML workflow. It works in a network mode for roads, junctions, connections and signals, a demand mode for vehicles, routes, persons and stops, and a data mode for edge data and traffic analysis zones, and it provides unlimited undo, snapping and keyboard shortcuts. Because it is built directly on netconvert, anything it saves is a valid network compiled by the same code.

Networks can also carry **elevation**. Heights can come from OSM, OpenDRIVE or shapefiles, be added from height maps (`--heightmap.shapefiles`, `--heightmap.geotiff`), be given as z values in edge shapes, or be edited in netedit. Elevation does not influence plain car-following, but it is used by the electric-vehicle model, the PHEMlight emission model and the KraussPS car-following model, which accounts for slopes. **Geo-coordinates** are handled by the projection stored in the `location` element, with TraCI, sumolib and the GUI converting between network metres and longitude and latitude, and several outputs optionally written in geographic form.

## Specialised networks and export

Motorway scenarios need particular care. Ramps are best modelled as extra lanes that terminate, forcing vehicles to merge by lane changing, and because simulated drivers are cautious, acceleration lanes often have to be longer than in reality; lane reductions can instead be handled with a zipper node. Weaving sections that combine on- and off-ramps risk deadlock unless the connections are arranged so that the exit leaves from the two right-most lanes. Pedestrian networks require sidewalks, crossings and walking areas, generated through OSM options, heuristics such as `--sidewalks.guess`, or netedit. Turnaround behaviour is controlled with the `--no-turnarounds` family of options. Finally, netconvert can export to plain XML, OpenDRIVE, MATsim, DLR-Navteq and Amitran formats, and helper scripts produce GeoJSON and KML for use in GIS tools.
